## 7. 根因分析

### 7.1 直接原因

描述导致问题发生的最近一层原因。

### 7.2 促成因素

- 需求或范围是否不清晰：
- 设计是否遗漏失败路径：
- 测试是否缺少真实链路：
- 发布或配置是否不可重复：
- 监控是否未覆盖关键指标：
- 沟通和责任边界是否模糊：

### 7.3 五问法

1. 为什么发生？
2. 为什么没有提前发现？
3. 为什么测试或评审没有拦住？
4. 为什么恢复过程耗时？
5. 哪个系统性改动能降低再次发生的概率？

> “某个人不够仔细”通常不是可执行的根因。继续追问：为什么流程允许一次疏忽直接影响结果？

## 10. 改进行动项

行动项必须能关闭，避免“加强关注”“持续优化”这类无法验收的表述。

| ID | 行动项 | 负责人 | 截止时间 | 优先级 | 验证方式 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| A-01 |  |  |  | P0 / P1 / P2 |  | open |

一个合格行动项应包含：

- 明确动作：具体修改什么。
- 单一负责人：谁负责推进，不用“大家”。
- 截止时间：何时检查。
- 验证方式：用什么证据证明完成。
- 关闭条件：什么状态才算结束。

## 13. 30 分钟复盘会议议程

1. 0–3 分钟：确认范围、事实和非目标。
2. 3–8 分钟：回顾目标与实际结果。
3. 8–15 分钟：梳理关键时间线和主要问题。
4. 15–22 分钟：讨论根因与促成因素。
5. 22–27 分钟：确定行动项、负责人和验证方式。
6. 27–30 分钟：复述结论和下一次复查时间。

## 14. 主持人检查清单

- [ ] 先讲事实，再讲解释和评价。
- [ ] 区分“已验证”与“推测”。
- [ ] 让直接参与者补充关键上下文。
- [ ] 不在会议中无限扩展新议题。
- [ ] 每个重要问题至少对应一个处理决定。
- [ ] 每个行动项都有负责人和关闭条件。
- [ ] 会后把结论同步到任务的 source of truth。
